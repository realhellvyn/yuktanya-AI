# Release checklist — prototipe sintetis → pilot terkendali

Dokumen ini mencatat apa yang sudah dibuktikan kode dan apa yang masih menjadi blocker non-kode. Tidak ada klaim bahwa aplikasi sudah disetujui secara hukum.

## Pemeriksaan teknis (jalankan sekali sebelum pilot/rilis, bukan setiap perubahan)
1. `npm run check` (lint, typecheck, unit, DB). 2. `npm run build`. 3. `npm run test:smoke` (E01–E06 dan E08–E14; E07 hanya di tes DB). 4. `bash scripts/e2e/run.sh` dengan `VIEWPORTS` desktop dan mobile (lihat README). 5. `python3 -I scripts/validate_package.py`. 6. `grep -rniE "\bcap\b" src` hanya boleh menemukan komentar.
CI manual: GitHub Actions > check > Run workflow menjalankan job `check`, `smoke`, dan `e2e` (hanya `workflow_dispatch`). Catat hasil lari nyata (jumlah lulus/gagal, tanggal, commit) terpisah; berkas ini tidak mengklaim hasilnya.
Belum otomatis dan belum dijalankan: uji aksesibilitas manusia (layar 320/375/390/1280, zoom 200%, keyboard, pemahaman catatan; E18), uji Supabase Auth/Storage nyata, dan deploy Vercel produksi. Pemetaan skenario ke tes ada di `tests/e2e/SCENARIOS.md`.

## Konfigurasi wajib sebelum pilot
- Supabase: proyek, bucket privat `documents`, Auth, migrasi `supabase/migrations/*`, `SUPABASE_SERVICE_ROLE_KEY`, `DATABASE_URL`. Adapter Storage Supabase belum diverifikasi.
- `NEXT_PUBLIC_APP_URL` (URL kanonik untuk QR), `CRON_SECRET`, penjadwal yang memanggil `/api/jobs/outbox`, `/api/jobs/retention`, dan `/api/jobs/expire-orders` (penyapuan `expire_orders`, harian 00.45 WIB; ketiganya ada di `vercel.json`, header `Authorization: Bearer $CRON_SECRET`).
- `SUPABASE_SERVICE_ROLE_KEY` wajib di server agar penghapusan akun dapat menghapus akun Auth (soft delete lewat Admin API). Tanpa itu data tetap terhapus tetapi login belum ditutup (lihat `docs/RUNBOOK.md`).
- Penyedia email nyata (UNKNOWN; saat ini hanya mock) dan gateway pembayaran (UNKNOWN; saat ini hanya mock dan transfer manual). `MANUAL_PAYMENT_INSTRUCTIONS` harus diisi.
- **Blocker: konfirmasi baca dan pengingat lewat email belum berfungsi.** Belum ada adapter penyedia email nyata, jadi `EMAIL_PROVIDER` di produksi selalu dianggap tidak tersedia: halaman `/s/[token]` dan panel pemilik menyatakan "Konfirmasi baca lewat email belum tersedia", tidak ada tantangan kode yang dibuat, dan panel pengingat menyatakan email belum terkirim. Sebelum diaktifkan: pilih penyedia, tambah adapter, dan kirim kode konfirmasi (berlaku 10 menit) **langsung saat diminta** (cron outbox hanya harian, kode akan selalu kedaluwarsa); pengingat 08.00 WIB cocok dengan cron harian.
- `NEXT_PUBLIC_APP_URL` wajib URL `https://` kanonik di produksi. Bila kosong atau bukan https, halaman yang membuat tautan/QR (dokumen, hasil review, daftar, tautan berbagi) gagal dengan galat server (gagal tertutup), bukan memakai localhost.
- **Pembatas laju auth (audit C12).** Aplikasi membatasi masuk per IP+email dan per IP saja (sengaja tanpa batas per email untuk masuk, agar orang lain tidak dapat mengunci akun seseorang); daftar, minta atur ulang kata sandi, dan kirim ulang konfirmasi dibatasi per IP+email, per IP, dan per email (tabel `auth_attempts`, hanya hash; batas rekayasa di `src/lib/auth/rate-limit.ts`). Sejak migrasi 38 jendela dihitung dengan jam database (`now()`), bukan jam server aplikasi. BELUM DIVERIFIKASI di proyek nyata: CAPTCHA/Turnstile Supabase Auth (belum dipasang), batas laju bawaan Supabase Auth di dashboard, dan apakah GoTrue melihat IP klien atau IP server untuk panggilan dari aksi server. IP klien dibaca dari `x-real-ip`/`x-forwarded-for` (tepercaya di Vercel; di host lain dapat dipalsukan: untuk masuk hanya batas IP+email yang tersisa, sedangkan daftar/atur ulang/kirim ulang tetap punya batas per email). Bila database pembatas tidak dapat dihubungi, auth tidak diblokir (gagal-terbuka). Baris kunci di `auth_attempts` yang jendelanya dimulai lebih dari 2 hari lalu dibersihkan oleh retensi harian (`run_retention`, migrasi 38).
- **Header keamanan (audit C22).** CSP dengan nonce per permintaan dipasang oleh `src/proxy.ts`; header statis (X-Frame-Options DENY, nosniff, Referrer-Policy, Permissions-Policy, HSTS tanpa preload di produksi) oleh `next.config.ts`. Semua halaman dirender dinamis karena nonce. Setelah deploy, periksa header di domain produksi (mis. `curl -sI https://<domain>/`) dan konsol browser tanpa pelanggaran CSP. Bila login Google diaktifkan, `form-action` otomatis memuat asal Supabase dan `accounts.google.com`; uji alur itu di staging.
- Hosting produksi dan gateway LLM (`FREELLM_*`) belum ditetapkan.

## Flag produksi (semua default OFF)
`AI_PREREVIEW_ENABLED`, `DEEP_REVIEW_PURCHASE`, `ENHANCED_ISSUANCE`. Deep/Enhanced hanya dinyalakan setelah E04, E05, E09, E10, E11 lulus, rubrik M1–M7 disetujui mitra (`/admin/rubric`), dan kebijakan refund disepakati.

## Blocker non-kode (tidak diselesaikan oleh kode)
Blocker pilot dari review integritas (Task 12/13): (1) konflik kepentingan tingkat firma tidak dapat dicabut; permintaan berbayar milik pemilik itu kembali ke perutean admin, tetapi bila tidak ada firma lain yang dapat menerimanya permintaan tertahan dan sistem tidak punya jalur pengembalian dana karena konflik (perlu kebijakan mitra dan langkah manual); (2) menutup (`CLOSE`) order yang punya pembayaran `DISPUTED` tidak menuntaskannya: pembayaran itu tetap muncul di daftar rekonsiliasi `/admin/payments` sampai admin mencatat `REFUND_RECORDED`.

Persetujuan template oleh mitra hukum (`document_templates` harus `APPROVED` dengan hash cocok), kriteria dan rubrik hukum, klaim publik Legal Verified, kualifikasi/otorisasi profesional nyata, privasi dan persetujuan sebelum data nyata dikirim ke AI, penerbit/ruang lingkup publik (`PUBLIC_ISSUER_DISCLOSURE` tetap off), kebijakan refund/kredit, SLA, biaya AI dan mitra untuk margin, penilaian pajak dan entitas. Sign-off mitra yang masih harus dicatat: mitra setuju namanya disebut kepada klien pada hasil pemeriksaan (halaman hasil menampilkan nama firma pemeriksa).

## Celah yang diketahui
Metrik AI (`admin_overview`) mencampur beberapa tugas: `chat` (hanya riwayat; rute `/api/ai/chat` dihapus di Task 13), `document_chat`, `template_chooser` ("Saya belum tahu", Task 14), dan `ai_review` (dibedakan lewat metadata `task`, belum dipisah per tugas di tampilan); pekerjaan deep yang ditahan tetap berstatus ON_HOLD setelah refund/tutup; refund dan neto belum dipecah per jenis layanan; beberapa kasus smoke (E02 reviewer satu firma tak ditugaskan, E05 standar belum selesai, E10 catatan material belum selesai, E11 penugasan basi, E14 dokumen ke-6 Member, hash tidak cocok) belum punya kasus smoke tersendiri meski dicakup tes DB; Pembatas laju publik berada di memori per proses; unggahan PDF/DOCX/TXT ada di balik flag `AI_PREREVIEW_ENABLED` (pembacaan dalam proses, tanpa worker/sandbox dan tanpa pemindaian malware); tidak ada jalur reinstate untuk verifikasi yang ditangguhkan; revoke oleh reviewer penerbit langsung (kebijakan menyebut hanya permintaan pencabutan). Konflik kepentingan (Task 12, diperbarui Task 13): konflik tingkat firma hanya dapat dicatat (tidak dapat dicabut); saat dicatat, penugasan aktif berakhir dan semua permintaan pemilik itu yang masih berjalan di firma itu kembali ke perutean admin (`/admin/routing` menampilkan tanda konflik) untuk dialihkan ke firma lain, tetapi pengembalian dana karena konflik belum ada di sistem (perlu kebijakan mitra dan langkah manual); konflik per reviewer hanya lewat pernyataan reviewer saat terbit/memutuskan, tanpa daftar konflik terstruktur; penghapusan Legal Note draf (`delete_note`) belum dicatat di audit.

## Langkah manual staging (pemilik proyek, lewat SQL editor dashboard Supabase)
Alat MCP membatalkan `DROP` dan `delete from`, jadi langkah ini dijalankan manusia. Semua data staging sintetis. Jalankan berurutan; setelah tiap langkah jalankan pemeriksaannya.

**A. `delete_note` (dari `20261016000021_report_publish.sql`).** Membutuhkan `load_draft` (sudah ada di staging sejak migrasi 21). Tempel persis:
```sql
create or replace function public.delete_note(p_reviewer uuid, p_request uuid, p_revision integer, p_note_no integer, p_now timestamptz)
returns integer language plpgsql security definer set search_path = public as $$
declare v_rep public.review_reports%rowtype;
begin
  v_rep := public.load_draft(p_reviewer, p_request, p_revision, p_now);
  delete from public.legal_notes n where n.report_id = v_rep.id and n.note_no = p_note_no;
  update public.review_reports rp set revision = rp.revision + 1 where rp.id = v_rep.id;
  return v_rep.revision + 1;
end;
$$;
revoke execute on function public.delete_note(uuid, uuid, integer, integer, timestamptz) from public, anon, authenticated;
grant execute on function public.delete_note(uuid, uuid, integer, integer, timestamptz) to service_role;
```
Periksa: `select proname, prosecdef, proconfig from pg_proc where proname = 'delete_note';` → satu baris, `prosecdef = true`, `proconfig` memuat `search_path=public`; `select has_function_privilege('authenticated', 'public.delete_note(uuid,uuid,integer,integer,timestamptz)', 'execute');` → `false`. Catatan PUBLISHED tetap tidak dapat dihapus (trigger `legal_notes_guard`).

Isi: `auth_attempt_allowed` memakai jam database (`now()`), parameter `p_now` tetap diterima tetapi diabaikan (tanda tangan sama; aplikasi lama dan baru tetap berjalan); `run_retention` juga membersihkan `auth_attempts` yang jendelanya dimulai lebih dari 2 hari lalu dan mengembalikan kunci `auth_attempts`; indeks `auth_attempts_window_idx`. Urutan: 37 → 38; deploy aplikasi kapan saja sesudahnya. Periksa: `select run_retention(now(), 100);` memuat kunci `auth_attempts`; `select has_function_privilege('authenticated', 'public.run_retention(timestamptz,integer)', 'execute');` → `false`.

## Kebijakan retensi & penghapusan — bawaan rekayasa (menunggu persetujuan mitra hukum)
Rincian lengkap di `docs/RUNBOOK.md`. Ringkas: `ai_attempts` dihapus setelah 30 hari, `ack_challenges` 7 hari setelah kedaluwarsa, kunci pembatas laju auth (`auth_attempts`, hanya hash) 2 hari setelah awal jendelanya (harian 02.30 WIB, per batch, idempoten). Pengguna dapat mengunduh datanya (JSON, hanya milik sendiri) dan menghapus akun dari `/settings`. Penghapusan: konten pemilik dihapus; pesanan/pembayaran/audit disimpan tanpa email untuk rekonsiliasi; dokumen yang sudah diperiksa profesional atau punya verifikasi publik dipertahankan barisnya dengan hash (agar `/verify` tetap bekerja) tetapi judul/isi dikosongkan; laporan & catatan profesional yang sudah terbit tidak diubah. Penghapusan ditolak selama ada Review Standar atau Pemeriksaan Mendalam berjalan (deep ON_HOLD hanya selama pesanannya belum dibatalkan/dikembalikan), kasus khusus terbuka, pembayaran menunggu atau dalam pencocokan, atau untuk akun staf; tiap alasan punya pesan sendiri. Semua angka dan aturan ini harus disetujui mitra hukum sebelum pilot dengan data nyata.
